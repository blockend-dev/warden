## What this proves

- The current, security-fixed Warden contract (the same source
  `packages/contracts/src/warden.compact` ships, `blockTimeLte`
  expiry-enforcement included) can be deployed to Midnight Preprod.
- Real ZK proofs can be generated for `createMandate`, `authorize`, and
  `revoke` against that deployment.
- Real transactions can be submitted and included on-chain.
- The web application's own server/API execution path — not just a
  standalone script — can execute the full mandate lifecycle against the
  deployed contract.
- Spending-cap enforcement is enforced on-chain: an over-cap request is
  rejected by the deployed circuit itself.
- Revocation enforcement is enforced on-chain: a request that succeeded
  before revocation is rejected after it, by the deployed circuit itself.

## What this does not claim

- **Not** a mainnet deployment. This is Midnight Preprod, a test network.
- **Not** a production-grade multi-tenant custody architecture. The live
  backend uses one shared server-side wallet for the whole deployment —
  documented, deliberate scope for a judge-facing demo, not an oversight.
- **Not** exhaustive security verification of the live path. The protocol's
  adversarial coverage (36 named attack-scenario tests) runs against the
  simulator, exercising the same compiled circuit logic — see
  [`docs/THREAT-MODEL.md`](THREAT-MODEL.md). The live run above proves the
  deployment and integration work end to end; it is not a second, separate
  adversarial audit of the live path itself.
- **Not** every possible protocol path live-tested — the table above is
  the full mandate lifecycle (create, authorize twice, revoke, authorize
  again), not every circuit branch (e.g. action-count exhaustion was not
  separately exercised live; it is covered by the simulator suite).
- **Not** a claim that the hosted Railway deployment has itself been
  verified live — the evidence above is from a local run of `apps/web`
  against real Preprod, using the same code Railway runs. Whether the
  actual hosted Railway service has `WARDEN_NETWORK=preprod` configured
  and has completed its own sync is a separate, deployment-specific fact —
  check that deployment's own environment badge or
  `GET /api/network-status`, don't assume it from this document.

## Environment distinction

Two backends exist, and this repository never presents one as the other:

- **`preprod`** (`WARDEN_NETWORK=preprod`) — real execution against
  Midnight Preprod, exactly as evidenced above. Requires a funded
  server-side wallet, a reachable proof server, and a multi-hour first
  sync (see `docs/DEPLOY-RAILWAY.md`).
- **simulator** (the default when `WARDEN_NETWORK` is unset or anything
  else) — real compiled circuits executed in-process via
  `@midnight-ntwrk/compact-runtime`, no proof server, no live network.
  Deterministic, instant, funding-free — the correct fallback for local
  development and for any deployment that hasn't configured Preprod.

The environment badge and `GET /api/network-status` always reflect which
one a given running instance is actually using — read live from the
server, never hardcoded, and never `LIVE` unless the Preprod connection
has genuinely finished initializing. See
[`packages/sdk/src/network.ts`](../packages/sdk/src/network.ts) and
[`apps/web/src/server/network.ts`](../apps/web/src/server/network.ts).
